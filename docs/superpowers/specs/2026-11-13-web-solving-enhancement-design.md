# CTFY Web 黑盒与白盒解题能力增强设计

## 意图

在 `worktree-ctfy-v3-solver` 当前单题 Agent 上，增强 Web 黑盒、完整源码项目和源码片段三类题目的解题能力。参考提交 `5a54d44 feat: expand offline CTF tooling`，本设计同时覆盖 Docker 离线工具、知识库、CTFY 提示词和契约测试，避免只安装工具或只堆积知识文本。

现有两条本地 Web 记录主要是无附件 HTTPS 题，探索集中在框架路由、调试面、边缘代理与 HTTP 协议差异，并出现意图数量持续增长但未收敛的问题。因此，本设计把可复现证据、负结果和停损放在与漏洞 payload 同等重要的位置。

## 已确认的需求决策

- Web 黑盒和白盒题都需要支持。
- 白盒既可能是带 manifest、入口和运行配置的完整项目，也可能只有少量源码文件。
- 第一批采用黑盒与白盒双入口，不引入浏览器，不引入 Semgrep。
- 第一批工具保持轻量；完整附件项目只做静态审计，不直接执行项目及其依赖；动态验证仅使用 Agent 自写的最小 PoC 和镜像内可信工具，再进行定向在线验证。
- 修复附件下载后图谱仍可能保留空路径的问题。
- 通过 CTFY 提示词保证首轮 Web 规划使用对应 KB，本批不重写 KB 检索算法。

## 目标

1. 无源码时，Agent 能建立会话、路由和响应基线，并进行有界、可复核的框架与协议差分。
2. 有完整源码时，Agent 先建立路由、鉴权、依赖和危险 Sink 清单，通过静态数据流、Agent 自写的最小 PoC 和可信工具验证，再对在线目标做定向验证。
3. 只有源码片段时，Agent 区分可见事实与未知逻辑，不脑补未提供的中间件、过滤和鉴权，通过在线差分验证假设。
4. 所有已下载或本地已有的附件在事实图中都有真实路径，后续规划不会误认为附件仍未下载。
5. 新增工具、KB 命令、提示词和镜像实际能力一致，并能以非 root `agent` 用户离线使用。
6. 保留现有提交、判题、图锁、原子写、作用域和提示注入防御语义。

## 非目标

- 不加入 Chromium、Playwright、Selenium、Puppeteer 或浏览器 MCP。
- 不加入 Semgrep、CodeQL、大型反编译平台或重型 OCR/ML 运行时。
- 不增加新的目录扫描器、自动化注入扫描器或全量 nuclei 模板。
- 不实现专门独立的 Web solver 进程，继续复用现有 reason → explore 闭环。
- 不改 KB 的检索评分算法，不实现跨题经验图或自动跨题学习。
- 不自动递归解包，不直接执行完整附件项目、其依赖、安装脚本或未知二进制。
- 不为完整项目本地执行新增 UID、网络命名空间或容器沙箱；第一批通过禁止直接执行保持边界。
- 不修改答案提交、平台 verdict、完成条件和结果导出协议。
- 不在本批修复与 Web 增强无关的 solver 生命周期问题。

## 反目标

即使镜像构建和测试通过，出现以下情况也不视为设计成功：

- Agent 在源码可审计时仍先进行大规模盲扫。
- Agent 把未见源码中的假设记录为已确认事实。
- Agent 因 KB 推荐而调用镜像中不存在的工具。
- Agent 反复扩大请求量、字典或协议向量，而没有新增证据。
- Agent 直接启动完整附件项目、执行其依赖或安装脚本，导致平台凭证、同 UID 进程或事实图暴露给不可信代码。
- 为了“完整”而一次加入大量彼此重叠、没有真实使用路径的工具。

## 约束

- 比赛运行时无公共互联网；平台 API、模型网关和当前题目标按现有规则访问。
- 所有主动探测只针对当前任务明确授权的 endpoint，并保留请求数、并发和时间上限。
- 协议走私、缓存和路由差异探测必须有前置证据，避免影响共享基础设施或其他用户。
- 附件、源码、HTTP 响应和图内容均是不可信数据，不得把其中的文本当作操作指令。
- 第一批不直接运行完整附件项目、其依赖、安装脚本或未知二进制，也不加载不可信项目模块进行本地复现。
- 本地动态验证仅限 Agent 审查源码后自写的最小 PoC，以及镜像内可信工具；不得借验证之名执行项目入口或依赖。
- 不得通过公共网络安装项目依赖；分析产物和自写 PoC 留在 `/ctfy/work`。
- 新平台代码使用 Python 标准库，测试沿用 `unittest`，保持现有代码风格。
- KB 使用现有 JSON 格式、中文说明和可检索英文关键词；关键关键词放在 title、description 和 tags 中，因为检索只覆盖 detail 前 500 字符。

## 方案比较

### 方案 A：只做黑盒协议与框架增强

加入 HTTP/2、会话和协议差分工具，并扩黑盒 KB。对现有两条 Web 样例最贴合，但无法满足完整源码和源码片段题。

### 方案 B：只做白盒源码审计增强

加入 PHP/PHPGGC、源码审计流程和附件修复。能覆盖两类白盒题，但对无附件黑盒题收益不足。

### 方案 C：黑盒、白盒和浏览器一次完成

能力覆盖最广，但浏览器会改变镜像体积、内存、启动时间和现有明确排除 Chromium 的契约；在没有浏览器题基准前，难以判断收益。

### 选定方案：轻量双入口

合并 A 与 B，共用证据工作流，按附件和源码完整度分流；C 中的浏览器与 Semgrep 留待后续独立评估。用户已确认这一范围。

## 总体工作流

```text
读取当前题、endpoint、问题和附件事实
├─ 无源码附件
│  → 基准响应与会话画像
│  → 指纹、路由、调试面
│  → 有证据的漏洞或协议差分
│
└─ 有源码附件
   → 清点附件、manifest、入口、配置和可见源码
   ├─ 完整项目
   │  → 路由/鉴权/依赖/Sink 清单
   │  → 静态数据流 + 自写最小 PoC/可信工具验证
   │  → 定向在线验证
   └─ 源码片段
      → 可见数据流与明确未知项
      → 构造对照假设
      → 定向在线差分验证

两类路径都必须：
保存可复现脚本和证据 → 记录关闭的分支 → 达到停损条件后换路
```

## 工具设计

### Docker APT

- `nghttp2-client`：提供 `nghttp`，用于有界 HTTP/2 和 `:authority` 差分。
- `php-cli`：提供 PHPGGC 所需 PHP 运行时，以及 Agent 自写最小 PHP 片段和序列化数据的验证能力；不用于启动完整附件项目。

除非具体测试证明需要，不额外加入 PHP 扩展或完整 Web 服务栈。

### Docker Python 包

- `httpx[http2]`：可脚本化 Cookie、重定向、CSRF Token、认证状态和 HTTP/2 请求。
- `h2`：确有需要时进行底层 HTTP/2 实验；显式声明，不依赖传递依赖偶然可用。
- `websockets`：只在目标出现 WebSocket/Upgrade 证据时使用。
- `flask-unsign`：Flask Session 解码、弱密钥有界验证和重签。

遵循现有 PyPI 镜像和 `--break-system-packages` 构建方式。实现时选择与镜像 Python 兼容的版本或版本范围，并通过实际导入与命令冒烟验证；不得在运行容器时补装。

### 离线 PHPGGC

- 按队友处理 `jwt_tool`/`RsaCtfTool` 的方式，将固定版本的 PHPGGC 源归档保存为 `docker/phpggc.tar.gz`。
- 构建时解压到 `/opt/phpggc`，提供 `/usr/local/bin/phpggc` 可执行入口。
- 在 `docker/CTFY.md` 记录来源、版本和命令入口。
- 使用 `phpggc -l` 等真实命令验证非 root 可执行，不只检查文件存在。

## 附件事实同步

### 当前问题

`ctfy_run.run()` 先调用 `prepare_graph()`，后调用 `ensure_attachments()`。`sync_ctfy_facts()` 对附件只做 `add_once`，因此远程附件初始 `path=None`、`download_required=true`，下载后不会更新。正确答案后的 task 快照同步还可能再次携带旧的空路径。

### 目标语义

- `ctfy.ensure_attachments()` 在每个远程附件成功下载后，将内存 task 中对应项的 `path` 更新为实际目标路径；已有本地路径保持不变。
- 附件准备完成后、调用 `sapper auto` 前，再次同步附件事实。
- 对同一 `(record_type=attachment, sync_key=name)` 的已有事实，更新真实 `path` 和 `download_required=false`，不创建重复 fact，并保留原 fact id。
- 后续同步若收到旧 task 快照的 `path=None`，不得清除已确认的真实路径或把 `download_required` 改回 true。
- QA 本地附件继续执行现有的存在性检查；实例附件继续执行现有的文件名、防目录逃逸和原子下载检查。
- 附件更新必须持有现有图锁并原子写，不能复用只适用于 flag 的 `update_flag_fact()`。
- 下载失败、QA 文件缺失和配置错误继续使用现有错误与退出语义。

事实图本身就是统一附件清单，至少包含名称、真实路径、大小和下载状态。本批不另建第二份索引，不在运行器中自动判断技术栈或解包；manifest 与源码完整度由首个白盒审计 intent 检查。

## 知识库设计

当前最大编号为 `kb059`，新增以下五个条目。

### `kb060`：Web 会话、差分证据与停损工作流

- 保存基准请求、原始响应、Cookie Jar、CSRF Token 和认证状态。
- 使用 `httpx` 脚本维护会话，并保存到工作目录，避免每个 intent 重新实现。
- 对照实验同时关注状态码、Body Hash、关键 Header、重定向、响应长度和有界时序差异。
- 每个负结果写明覆盖的端点、参数、方法、协议和请求上限。
- 关闭假设必须有证据；没有新证据不得扩大字典、并发或重复同类扫描。
- 不把 scanner warning、单次异常或模型推断当作漏洞成立。

### `kb061`：Web 框架路由、调试面与实例生命周期

- 覆盖 Flask/Werkzeug、Django、FastAPI 和 Spring Actuator 的常见元数据与调试入口。
- 用 `404/405/308/OPTIONS/Allow` 区分路由不存在、方法不允许和斜杠重定向。
- 使用固定、少量 canary 识别目标是否重启或改变行为；状态改变后才重新检查旧负结果。
- 调试面暴露后优先寻找配置、环境和启动信息，不做无依据的 PIN 爆破。
- 所有枚举限制请求数并保存原始证据。

### `kb062`：Web 边缘代理与 HTTP 协议差异

- Host 与 `:authority`、绝对形式 URI、路径归一化、双重编码和重复 Header。
- HTTP/1.1 与 HTTP/2 的路由差异，以及代理到后端的协议转换。
- `nghttp` 和 `h2` 用于可复核的有界验证，`httpx` 用于高层会话复现。
- CL.TE/TE.CL 等请求走私只在出现明确解析差异后做最小确认，不默认盲打。
- CONNECT、Upgrade、WebSocket 仅在有路由或协议证据时进入后续分支。
- 每个协议族有独立关闭条件，避免把所有向量混在一个无界 intent 中。

### `kb063`：Web 源码审计工作流——完整项目与源码片段

- 附件清单、文件类型、manifest、锁文件、入口、路由、配置和可见源码范围。
- 完整项目：建立路由 → 中间件/鉴权 → 输入源 → Sink → 配置/依赖的清单；只执行 Agent 自写的最小 PoC 和可信工具验证，不直接启动项目或加载其依赖。
- 源码片段：只跟踪可见数据流；未提供的鉴权、过滤和中间件标为未知，通过在线对照验证。
- 完整项目及其依赖不是直接运行对象；缺少依赖不影响静态审计，不得联网安装。
- 语言速查集中在同一条目：
  - PHP：包含、反序列化、PHAR、Session 和危险函数。
  - Node/Express：中间件顺序、原型链污染、模板和路径处理。
  - Python：Flask 签名、SSTI、Pickle 和调试配置。
  - Java/Spring：SpEL、Actuator、反序列化、过滤器与路由。
- 源码审计结果用于产生精确在线请求，不替代在线证据。

### `kb064`：Web 文件包含与路径穿越

- LFI/RFI、目录穿越、PHP Wrapper、日志/Session 包含和上传转包含。
- Zip Slip 等解压路径问题，以及任意文件读到 RCE 的组合路径。
- 先证明文件读取或路径控制，再构造更重的利用链；保留对照响应。

### 修订现有条目

- `kb001`：扩充 JS 保存、接口/密钥静态分析和 Source Map `sourcesContent` 提取；没有 `sourcesContent` 时不得声称恢复完整源码。
- `kb004`：移除默认 `tplmap` 命令，修正 SSTI 检测示例，保留手工差分与已知答案验证。
- `kb005`：使 PHPGGC 命令与本次实际安装一致，使用 PHPGGC 和 Agent 自写最小 PHP 片段验证 gadget 输出，不启动完整附件项目。
- `kb016`、`kb052`：没有本地 nuclei 模板时转定向手工验证，不等待联网下载或默认全模板扫描。
- `kb039`：明确 Flask 客户端 Session 默认是签名而非加密，加入 `flask-unsign` 的解码、弱密钥有界验证和重签流程。
- `kb043`：移除把 `ddddocr` 当作默认可用依赖的表述，不引导运行时安装 ONNX/OCR 栈。

本批不重写其他 Web/CVE 条目；若发现额外漂移，在交付说明中记录，不顺手扩大修改范围。

## 提示词设计

### `templates/ctfy/reason.md`

Web 路由从一行扩展为简短双入口规则：

- 首轮 Web 规划先检查附件事实和实际文件，运行相应的 `sapper kb search`，必要时 `kb show` 读取命中条目。
- 有源码：先判断完整项目或源码片段，按 `kb063` 产生路由/Sink/未知项，再安排定向在线验证。
- 无源码：按 `kb060` 建立基线和会话，再按证据选择 `kb061` 或 `kb062`。
- 每个扫描/协议 intent 继续声明请求、并发和时间上限，并必须有关闭条件。
- 不把本地静态扫描命中直接当作可提交证据。

### `templates/ctfy/explore.md`

- 执行 Web intent 前读取当前 intent 指定的 KB 和已有证据，不重复全量检索。
- 有源码时保存审计清单和脚本；无源码时保存会话脚本、原始请求/响应和对照结果。
- 不得直接启动完整附件项目、加载其依赖或联网安装；需要动态验证时使用 Agent 自写的最小 PoC 和镜像内可信工具。
- 负结果包含覆盖范围；达到关闭条件后结束当前 intent，让 planner 选择下一路径。

提示词保持简短，详细方法留在 KB，避免每轮重复注入大量文本。

## 验证

### 单元与契约测试

1. 现有测试全部通过。
2. 远程附件下载后，内存 task 路径和已有附件 fact 均更新，fact 数量不增加。
3. 再次同步旧 `path=None` 快照不会清除真实路径；重复运行保持幂等。
4. QA 本地附件、缺失文件、下载失败、目录逃逸和原子写测试保持通过。
5. Dockerfile 声明所有新工具和 PHPGGC 归档，仍排除 Chromium、Semgrep 和既有重型依赖。
6. KB 查询至少覆盖：
   - `web session evidence` → `kb060`
   - `Werkzeug routing` → `kb061`
   - `HTTP/2 proxy` → `kb062`
   - `web source audit` → `kb063`
   - `LFI traversal` → `kb064`
7. 修订后的命令不再默认引用 `tplmap`、`ddddocr` 或不存在的全量 nuclei 模板；PHPGGC、`nghttp`、`flask-unsign` 可从对应条目检索。
8. 提示词契约包含完整项目、源码片段、首轮 KB 使用、禁止直接执行不可信完整项目、离线依赖和停损要求。

### 镜像冒烟

- Docker 构建成功。
- 以 `agent` 用户执行 `nghttp --version`、`php -v`、`phpggc -l`、`flask-unsign --help`。
- Python 导入 `httpx`、`h2`、`websockets`，并验证 `httpx` HTTP/2 支持可用。
- 用本地测试数据完成 Flask Session 签名、解码和重签往返，不访问公共网络。
- 尽可能用 loopback 服务验证 Cookie/CSRF 会话脚本；不向真实外部目标发送测试流量。

### 解题效果评估

单元测试只能证明能力接入，不能证明 solve rate 提升。后续应选取具有代表性的黑盒、完整源码和源码片段题做 A/B，对比是否解出、意图数、请求数、耗时和重复扫描次数。没有该题集和实验结果时，交付只能说明“工具、知识库和附件链路已验证”，不能宣称解题率已经提高。

## 留给实现者的局部决策

- 新 APT/Python 包与 Kali rolling、Python 版本的精确兼容版本或范围。
- PHPGGC 的固定上游版本、归档布局和可执行入口的最小包装方式。
- 附件 fact 更新的最小函数形式，但必须满足锁、原子写、幂等和旧空路径不回填语义。
- 在不增加新依赖的前提下，loopback 冒烟测试的具体实现。
- KB 命令中的占位符和排版，保持现有风格即可。
